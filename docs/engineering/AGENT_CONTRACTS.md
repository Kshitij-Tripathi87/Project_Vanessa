# Agent contracts

**Status:** the wire contract is implemented and strict; the *proposed* unified
agent envelope from the product brief is not. This document records what the
system actually exchanges, and what the brief would add.

## The wire contract (implemented)

Defined in `packages/protocol/src/messages.ts`. Every schema is `.strict()`, so an
unknown field is a protocol error rather than a silently ignored one.

### Phone → PC: `task.submit`

| Field | Type | Note |
|---|---|---|
| `requestId` | UUID | Generated by the phone; now also supplied into the bridge so the UI's pending state and the signed frame name the same request |
| `idempotencyKey` | string, 8–128, `[A-Za-z0-9._-]` | Prevents duplicate execution across retries |
| `capability` | `^[a-z][a-z0-9_]{1,63}$` | Validated before the frame is built |
| `canonicalArguments` | bounded record, ≤32 keys | The exact object that is hashed for approval |
| `intent` | string ≤300, optional | A natural-language hint. Never a command line. |

### PC → phone: `task.accepted`

`requestId`, `taskId`, `state: "accepted"`, `taskVersion`, `eventSeq`, `acceptedAt`.

`taskVersion` and `eventSeq` are per-task ordering facts. They are what a
snapshot-versus-live-event comparison would need if the phone ever gains a
snapshot timestamp; today the reducer uses `eventSeq` only to order a replay batch
against itself.

### PC → phone: `task.confirmation_required`

Carries `approval: ApprovalRequestSchema`:

`approvalId`, `taskId`, `taskVersion`, `deviceId`, `capability`,
`capabilityVersion`, `consequence` (≤500), `target {kind, value}`, `actionHash`
(SHA-256 hex), `policyVersion`, `expiresAt`, and `eventSeq` alongside it.

The Android reducer refuses an approval missing `approvalId`, `taskId`,
`actionHash`, `deviceId`, or a positive `expiresAt`. An approval that cannot be
bound cannot be signed, and one that cannot be signed must not be offered.

### Phone → PC: `task.confirmation`

`approvalId`, `taskId`, `actionHash`, `decision: approved|denied`, `approvedAt`,
plus a separate biometric-bound signature. The phone re-sends the action hash it
saw, so the PC can reject a decision that was bound to a different action.

### The hashing contract

`ApprovalBindingSchema` names the exact field set that `computeActionHash`
hashes, and `computeApprovalDigest` on the orchestrator side derives the digest
the approval is checked against. `canonicalArguments` must be the parsed object,
not a JSON string, so both sides hash the same bytes.

> **Rule:** if the binding field set changes, the phone and the PC change
> together, and an approval minted across the change is invalid. There is no
> version negotiation for this today.

## What the brief proposes, and its status

| Proposed | Status |
|---|---|
| `task_id`, `request_id`, `parent_task_id`, `agent_id`, `capability`, `input`, `context_ref`, `policy`, `timeout_ms` | **Not implemented.** No `parent_task_id`, no `context_ref`, no `policy` block on the wire. |
| Response with `output`, `evidence[]`, `error`, `started_at`, `completed_at` | **Partially.** `recordAgentResult` records an outcome and verification; there is no `evidence[]` array in the transport. |
| One envelope for every agent | **No.** Agents return their own typed results; the catalog's `returns` string documents each one. |

### Recommendation

Do not introduce the proposed envelope alongside the existing one. The strict
schemas are the safety property — an extra field is an error, not a no-op — and a
parallel envelope would be the second correlation mechanism this project has
already had to remove once.

If `parent_task_id` or `evidence[]` are needed, add them to `messages.ts`, bump
the protocol version, and update both ends in one change.
